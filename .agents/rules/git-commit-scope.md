# 喵岛提交规范

## 每个问题单独提交

- 动手前先确定当前分支、工作区已有改动，以及这次需要拆成哪些独立问题。每完成一个可验证的小改动就单独暂存和提交。
- 一笔提交只解决一个能用一句话说明的问题，并包含该问题所需的实现、测试和直接依赖。以可独立审查、验证和回退为拆分标准。共享工具若服务多个问题，可先独立提交，让后续提交按顺序依赖它。
- 同一任务里的多项要求也要拆分。例如「板块冷启动首滑」「详情退场释放」「回复编辑器」「搜索」「大图」应各自提交。顶栏功能、通用重构和测试版版本号分别提交。
- 若多个改动碰巧在同一文件，按差异块暂存。用 `git add -- <路径>` 暂存完全归属该问题的文件，用 `git add -p` 或定向补丁暂存混合文件。已有的用户或其他代理改动、临时日志和抓帧文件留在原处。避免使用 `git add .` 或 `git commit -a`。

## 提交前核对

- 看 `git diff --cached --stat` 和 `git diff --cached`，确认每处暂存改动都直接支撑该提交的目标。运行 `git diff --cached --check`。发现混入内容就先调整暂存区。
- 每笔提交都应保持代码可编译。验证按任务要求和风险安排，遵守用户指定的编译次数。未实际运行的检查写成「未验证」。
- 标题用 `fix(scope): …`、`perf(scope): …` 等格式说清具体改动。可用 `perf(thread): defer list disposal until scrolling settles`。只有抓帧结果支持时才写「消除卡顿」等结论。
- 性能汇报写明对比的提交、设备、刷新率、手势、样本次数和仍存在的超时帧。区分编译、单元测试、真机验证。没有同条件对照时，把结论标为初测。

## 分支与交付

- 提交后用 `git show --stat HEAD` 核对范围，向用户汇报每笔提交的哈希、改动和验证结果。
- 用户要求推送时，默认推送到当前对应的开发或发布分支。只有用户明确要求合并时，才合入 `main`。已有提交的拆分或历史重写须另行获得授权。
